AI production readiness checklist

Use this before an AI system goes in front of users. It covers the work that separates a prototype from something a team can depend on. Nothing here is specific to a vendor, a model or a framework, and you are free to copy it into your own repository and adapt it.

Most of the items below are unglamorous and most get scoped last. That is the reason production launches slip. Working through them before the launch date is set is considerably cheaper than discovering them afterwards.

How to use it

  • Walk it before the launch date is committed, not after.
  • Any item you cannot answer is scope that has not been costed yet.
  • A "no" is not a blocker on its own. An undiscussed "no" is.

Interface contract

Every team downstream is blocked until these are fixed. Settle them before tuning anything.

  • 1.1Input schema is defined and validated at the boundary, with malformed input rejected rather than coerced.
  • 1.2Output schema is defined, including the shape returned when the system declines to answer.
  • 1.3Latency budget is agreed with whoever consumes the output, and the modeling approach fits inside it.
  • 1.4Error taxonomy exists: the caller can distinguish "no answer", "low confidence", "upstream failure" and "invalid request".
  • 1.5The contract is versioned, and there is a stated policy for breaking changes.

Failure behavior

Production systems are judged on what they do when they are wrong. Design this before the happy path.

  • 2.1Behavior on low confidence is defined: fall back, escalate to a person, or decline and say so.
  • 2.2Behavior when an upstream dependency times out or errors is defined and tested.
  • 2.3Fallback path exists and has been exercised, not just written down.
  • 2.4Degradation is graceful: one component misbehaving reduces capability rather than stopping the workflow.
  • 2.5Rate limits and cost ceilings are enforced, so a loop or a traffic spike cannot run unbounded.
  • 2.6There is a documented answer to "what does a user see when this fails".

Evaluation

If you cannot rerun the evaluation, you cannot safely change anything afterwards.

  • 3.1An evaluation set exists, is version controlled, and lives alongside the code.
  • 3.2It covers the awkward cases, not only the representative ones.
  • 3.3Every case that has caused an incident has been added to it.
  • 3.4It runs automatically when the model, prompt, retrieval or pipeline changes.
  • 3.5A pass threshold is agreed in advance, so the result is a decision rather than a discussion.
  • 3.6Results are recorded over time, so regressions are visible as a trend.

Observability

Conventional monitoring tells you the service responded. It does not tell you the response was sensible.

  • 4.1Input and output distributions are logged, so drift is visible against a baseline.
  • 4.2Confidence scores are recorded where the method produces them.
  • 4.3Fallback rate and human escalation rate are tracked. These usually move before anyone complains.
  • 4.4Latency is tracked at the percentiles that matter, not only the mean.
  • 4.5Cost per request is visible and attributable.
  • 4.6Alerting fires on rate of change, not only on absolute thresholds.
  • 4.7Logs are retained long enough to investigate an incident reported a week later.

Data and privacy

Usually the item that delays a launch when it is discovered late.

  • 5.1It is documented what data leaves your infrastructure, and where it goes.
  • 5.2Personal data handling has a lawful basis, and retention is defined.
  • 5.3Prompts and outputs containing personal or confidential data are excluded from logs, or redacted before they are written.
  • 5.4Vendor terms have been read on whether submitted data is used for training.
  • 5.5Deletion requests can be honored, including anything captured in logs or evaluation sets.

Rollout

Each stage exists to surface a different class of problem.

  • 6.1Internal use against real inputs, with no external consequence.
  • 6.2Limited cohort with human review on every output.
  • 6.3Wider cohort with review on flagged cases only.
  • 6.4General availability with monitoring and an unambiguous rollback path.
  • 6.5Rollback has been tested, not assumed.
  • 6.6Feature flag or equivalent allows disabling without a deploy.

Ownership

An unowned system becomes an unmonitored one, and an unmonitored system fails silently.

  • 7.1A named person owns it, not a team inbox.
  • 7.2There is a runbook covering the three most likely failures.
  • 7.3Someone other than the original author has run the deploy and the rollback.
  • 7.4Retraining or prompt revision has a defined trigger and a defined approver.
  • 7.5A review date is in the calendar, so nobody has to remember to look.

If most of this is already in place, the remaining work is probably smaller than it feels. If most of it is not, the gap between the prototype and the launch date is larger than the plan currently says, and it is better to know that now.
